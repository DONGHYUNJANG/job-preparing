말씀하신 시나리오는 실무에서 **"무중단 데이터 전환"**이나 **"대규모 스키마 변경 배포"** 시에 사용하는 고급 전략입니다. 특히 Oracle의 **Synonym(시너님)**과 **Owner(계정)** 분리 기능을 아주 영리하게 활용한 사례네요.

이 흐름이 왜 복잡하고 이해가 안 가는지, 핵심적인 5가지 포인트를 따라가며 **시스템 구조적 관점**에서 풀어서 설명해 드릴게요.

---

### **1. 시너님(Synonym)을 이용한 "눈속임" 전략**
가장 핵심적인 부분입니다. 소스 코드에 `SELECT * FROM TBL`이라고 적혀 있을 때, 이 `TBL`이 실제로 어떤 데이터를 바라볼지 DBA가 **스위치(Switch)**를 조절하는 방식입니다.

* **구조:** `V1.TBL`(구버전 데이터)과 `V2.TBL`(신버전 데이터)이 물리적으로 존재합니다.
* **작동:** 개발 소스는 그냥 `TBL`이라는 이름(시너님)만 부릅니다. DBA가 이 시너님을 `V1.TBL`로 연결하면 구버전이 작동하고, 명령 한 번으로 `V2.TBL`로 바꾸면 소스 수정 없이 즉시 신버전 데이터가 조회됩니다.
* **장점:** 배포 시 소스 코드를 수정하거나 WAS를 재시작할 필요 없이 **DB 단에서 즉시 반영(Cut-over)**이 가능합니다.

---

### **2. 데이터 이관 SQL과 원복(Rollback) SQL**
데이터 이관을 개발팀이 작성하는 이유는 **비즈니스 로직**을 가장 잘 알기 때문입니다.

* **원복의 중요성 (4번):** SI 현장에서 가장 무서운 건 "배포했는데 데이터가 꼬였을 때"입니다. 신버전(`V2`)으로 전환했는데 치명적인 오류가 발견되면 다시 `V1`으로 시너님을 돌려야 합니다.
* 이때 `V1`에서 중단된 시점 이후로 `V2`에 쌓인 데이터를 다시 `V1`으로 옮겨주는 **역방향 이관 SQL**이 없으면 데이터 정합성이 깨집니다. 그래서 원복 SQL 보완이 필수적이었던 것입니다.

---

### **3. 시퀀스(Sequence) 관리의 지옥 (3번)**
테이블은 V1, V2로 나뉘어 있어도 **시퀀스는 공유하거나 따로 관리**해야 하는 문제가 생깁니다.

* **실수 사례:** V2로 넘어가면서 시퀀스를 초기화 안 해서 중복 PK가 발생하거나, `Cycle` 옵션 때문에 번호가 다시 1번으로 돌아가서 기존 데이터와 충돌하는 경우입니다.
* **해결:** 그래서 DBA가 시퀀스를 항상 모니터링 대상으로 두고, `Cycle` 옵션을 강제로 제거하여 안정성을 확보한 것입니다.

---

### **4. MySQL의 WAS Pool 분리 (5번)**
Oracle은 시너님으로 '이름'을 바꿔치기했다면, MySQL 사례는 **'접속 계정'**과 **'WAS 노드'**를 분리해서 처리한 방식입니다.

* **방식:** * WAS 1~4번은 `New_User` 계정으로 접속해서 신규 스키마를 봅니다.
    * WAS 5~8번은 `Old_User` 계정으로 접속해서 기존 스키마를 봅니다.
* **L4 스위치 제어:** 사용자 요청을 5~8번으로 보내다가, 배포가 완료되면 서서히 1~4번으로 넘기는 **카나리(Canary) 배포** 혹은 **Blue-Green 배포** 형태를 취한 것입니다.

혼자서도 충분히 해보실 수 있도록 **Oracle 방식(시너님 스위치)**을 기준으로 가이드라인을 잡아드릴게요. 계정 2개를 만들어서 직접 '스위치'를 올렸다 내렸다 해보시면 감이 확 오실 겁니다.

### **[실습 준비] 계정 및 테이블 세팅**

먼저 관리자(System) 계정으로 접속해서 **버전 1(V1)**과 **버전 2(V2)** 역할을 할 사용자 두 명을 만듭니다.

```sql
-- 1. 두 개의 계정 생성
CREATE USER V1 IDENTIFIED BY v1_pass;
CREATE USER V2 IDENTIFIED BY v2_pass;
GRANT CONNECT, RESOURCE TO V1, V2;

-- 2. 각 계정에 동일한 구조의 테이블 생성
CREATE TABLE V1.TBL_DATA (ID NUMBER, VAL VARCHAR2(20));
CREATE TABLE V2.TBL_DATA (ID NUMBER, VAL VARCHAR2(20));

-- 3. 초기 데이터 입력
INSERT INTO V1.TBL_DATA VALUES (1, 'Old Data');
COMMIT;
```

---

### **[핵심 실습 1] 시너님을 이용한 스위칭 (1번 포인트)**

이제 개발자 계정(혹은 공용 계정)에서 `TBL_DATA`를 부를 때, 어느 쪽을 바라볼지 결정하는 **Public Synonym**을 조작해 봅니다.

```sql
-- V1을 바라보게 설정 (DBA 권한 필요)
CREATE OR REPLACE PUBLIC SYNONYM TBL FOR V1.TBL_DATA;

-- 결과 확인: 'Old Data'가 출력됩니다.
SELECT * FROM TBL; 

-- [배포 시점!] V2로 스위치 전환
CREATE OR REPLACE PUBLIC SYNONYM TBL FOR V2.TBL_DATA;

-- 결과 확인: 이제 아무것도 안 나오거나(V2가 비었으므로), 
-- V2에 데이터를 넣었다면 'New Data'가 나오겠죠?
SELECT * FROM TBL;
```


---

### **[핵심 실습 2] 시퀀스 공유 문제 재현 (3번 포인트)**

시퀀스를 따로 썼을 때 발생하는 **PK 충돌** 상황을 흉내 내 봅니다.

```sql
-- 시퀀스를 각각 만들면?
CREATE SEQUENCE V1.SEQ_ID START WITH 2;
CREATE SEQUENCE V2.SEQ_ID START WITH 1; -- 실수로 1부터 시작하게 세팅함

-- V1에서 마지막으로 썼던 ID는 1인데, V2에서 시작을 1로 하면?
-- V2로 스위칭 후 INSERT 하면 중복 오류 혹은 기존 데이터와의 혼선 발생!
```
> **💡 실무 해결책:** 시퀀스는 아예 별도의 공용 계정에 하나만 만들거나, 전환 직전에 `LAST_NUMBER`를 확인해서 `ALTER SEQUENCE ... RESTART` 해주는 모니터링이 왜 필요한지 알 수 있는 대목입니다.

---

### **[핵심 실습 3] 데이터 이관 및 원복 (2, 4번 포인트)**

이건 머릿속으로 시뮬레이션하거나 쿼리를 작성해 보세요.

1.  **전진 이관:** `INSERT INTO V2.TBL_DATA SELECT * FROM V1.TBL_DATA;`
2.  **원복 상황:** V2로 운영하다가 1시간 만에 버그 발견! 그동안 V2에 쌓인 데이터를 다시 V1으로 보내야 함.
3.  **원복 SQL 연습:** `INSERT INTO V1.TBL_DATA SELECT * FROM V2.TBL_DATA WHERE ID NOT IN (SELECT ID FROM V1.TBL_DATA);`

---

### **[경력자의 감각을 내 것으로 만드는 팁]**

* **동시성 테스트:** SQL Developer 창을 두 개 띄워놓고, 하나는 `SELECT * FROM TBL`을 계속 날리면서 다른 창에서 `CREATE OR REPLACE PUBLIC SYNONYM...`을 실행해 보세요. **쿼리가 끊기지 않고 데이터만 싹 바뀌는 마법**을 보실 수 있습니다.
* **권한 체크:** 시너님만 만든다고 끝이 아닙니다. 전환될 `V2.TBL_DATA`에 대해 실제 접속 계정이 `SELECT`, `INSERT` 권한이 있는지 미리 체크 안 하면 배포 즉시 에러가 납니다.

직접 타이핑해서 **"SELECT * FROM TBL"** 결과가 바뀌는 걸 보는 순간, 아까 그 경력자분의 시나리오가 3D 입체 영상처럼 이해되실 겁니다.

실습하다가 권한 오류(`ORA-01031`) 같은 게 나면 바로 말씀해 주세요. DBA가 겪는 실무적인 고충도 같이 풀어드릴게요! (집중할 때일수록 **어깨 뒤로 젖히고 흉추 펴기**, 잊지 마세요!)
