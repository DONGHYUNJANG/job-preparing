# Oracle Table Reorganization: 학생을 위한 완벽 가이드

안녕하세요! 오늘은 데이터베이스 관리의 중요한 유지보수 작업 중 하나인 '테이블 재구성(Reorganization)'에 대해 배워보겠습니다. 단순히 명령어를 따라 하는 것을 넘어, 왜 이 작업을 해야 하는지, 어떤 원리로 동작하는지, 그리고 각 단계에서 무엇을 주의해야 하는지 깊이 있게 이해하는 것을 목표로 합니다.

### **Part 1. 이론: 왜 테이블 재구성이 필요한가?**

우리가 사용하는 데이터베이스 테이블은 처음에는 깨끗하고 정돈된 책장과 같습니다. 하지만 시간이 지나면서 책을 넣고, 빼고, 다른 내용으로 바꾸는 과정에서 책장이 엉망이 됩니다. 테이블 재구성은 이렇게 엉망이 된 책장을 다시 깔끔하게 정리하는 작업과 같습니다.

#### **문제 1: 조각화(Fragmentation)와 HWM(High-Water Mark)**

테이블에 데이터가 계속 `INSERT`(입력)되면, 데이터 파일의 특정 위치까지 데이터가 차곡차곡 쌓입니다. 이때 데이터가 쌓인 가장 높은 위치를 **HWM(High-Water Mark)**, 즉 '최고 수위선'이라고 부릅니다.

그런데 만약 `DELETE` 명령어로 테이블의 데이터를 대량으로 지워도, **HWM은 줄어들지 않습니다.**

*   **비유**: 100페이지짜리 책에서 뒤쪽 50페이지를 찢어내도, 책의 목차는 여전히 '이 책은 100페이지까지 있다'고 기억하는 것과 같습니다.
*   **문제점**: Oracle이 테이블 전체를 읽는 작업(Full Table Scan)을 할 때, 실제 데이터가 없는 HWM 아래의 빈 공간까지 모두 읽으려고 시도합니다. 이는 불필요한 I/O(디스크 읽기/쓰기)를 발생시켜 성능을 저하시킵니다.

![HWM 설명 이미지](https'://i.imgur.com/5S3gC0b.png')
*(DELETE 이후에도 HWM은 그대로 있어, Full Scan 시 비효율 발생)*

#### **문제 2: 로우 체이닝(Row Chaining)과 마이그레이션(Row Migration)**

하나의 데이터 행(Row)이 너무 커서 한 블록에 저장되지 못하고 여러 블록에 나뉘어 저장되는 것을 '로우 체이닝'이라고 합니다.

더 흔하게 발생하는 문제는 '로우 마이그레이션'입니다.

1.  처음 `INSERT` 될 때는 행이 하나의 블록에 잘 저장되었습니다.
2.  이후 `UPDATE`로 인해 행의 길이가 늘어나면서, 기존 블록에 더 이상 담을 수 없게 됩니다.
3.  Oracle은 이 행 전체를 다른 빈 블록으로 옮기고(Migration), 원래 위치에는 "이사 갔음"이라는 쪽지(포인터)만 남겨둡니다.

*   **문제점**: 이 행을 읽으려 할 때마다, 원래 주소의 '쪽지'를 먼저 읽고, 그 쪽지가 가리키는 새 주소로 다시 찾아가야 합니다. 즉, 한 번이면 될 I/O가 두 번 발생하여 성능이 저하됩니다.

#### **해결책: `ALTER TABLE ... MOVE`**

`ALTER TABLE ... MOVE` 명령어는 이 모든 문제를 해결하는 마법 같은 명령어입니다. 이 명령은 테이블을 물리적으로 '이사'시킵니다.

1.  테이블의 실제 데이터만 읽어서 새로운 데이터 세그먼트(새로운 공간)에 차곡차곡 다시 쌓습니다.
2.  데이터가 없는 빈 공간은 모두 버리고, HWM은 실제 데이터의 가장 높은 위치로 초기화됩니다.
3.  로우 마이그레이션된 데이터는 새 위치에 완전히 저장되므로, 더 이상 '쪽지'를 찾아갈 필요가 없어집니다.
4.  결과적으로 테이블은 조각화가 제거된 매우 깨끗한 상태가 됩니다.

#### **중요한 부작용: 인덱스의 무효화**

테이블 데이터가 이사를 가면, 각 데이터의 물리적 주소(`ROWID`)가 모두 변경됩니다. 그런데 인덱스는 바로 이 `ROWID`를 저장하여 데이터의 위치를 빠르게 찾아주는 역할을 합니다.

`MOVE` 작업으로 인해 모든 `ROWID`가 바뀌었으니, 기존 인덱스는 이제 쓸모없는 주소들을 가리키는 '무효한(UNUSABLE)' 상태가 됩니다. 따라서 `MOVE` 작업 후에는 **반드시 `ALTER INDEX ... REBUILD` 명령어로 인덱스를 다시 만들어 주어야 합니다.**

### **Part 2. 실전: 완벽한 Reorg를 위한 계획**

이론을 알았으니, 이제 'SH' 스키마를 재구성하기 위한 구체적인 계획을 단계별로 살펴봅시다. 단순한 `MOVE`와 `REBUILD`를 넘어, 작업의 성공을 보장하고 최적의 성능을 이끌어내기 위한 추가 단계를 포함합니다.

> **🚨 가장 중요한 주의사항: LOGGING과 데이터 보호**
>
> 테이블 재구성과 같은 대규모 작업 시, 작업 속도를 높이기 위해 `NOLOGGING` 옵션을 사용하는 경우가 있습니다. 이 옵션은 Redo 로그 기록을 최소화하여 작업 시간을 단축시키는 장점이 있습니다. **하지만, 이는 매우 위험할 수 있습니다.**
>
> *   **`NOLOGGING`의 위험성**: `NOLOGGING`으로 수행된 작업은 Redo 로그에 기록되지 않으므로, 미디어 복구(Media Recovery)가 불가능합니다. 더 치명적인 것은, **데이터가드(Data Guard) 환경에서 Standby 데이터베이스로 변경 사항이 전송되지 않는다**는 점입니다. 만약 Primary 데이터베이스에서 `NOLOGGING`으로 테이블을 `MOVE`한 후 장애가 발생하여 Standby로 넘어간다면(Failover), 해당 테이블의 데이터는 손상된 상태로 남게 됩니다.
> *   **해결책: `LOGGING` 또는 `FORCE LOGGING`**: 모든 프로덕션 환경, 특히 Data Guard가 구성된 곳에서는 반드시 모든 작업이 로깅되도록 해야 합니다. 이것이 기본값(`LOGGING`)입니다. 데이터베이스 레벨에서 `ALTER DATABASE FORCE LOGGING;` 명령을 실행하면, 개별 객체의 `NOLOGGING` 설정을 무시하고 모든 변경사항을 강제로 로깅하여 실수를 방지할 수 있습니다.
>
> **이 가이드의 실습 절차에서는 안전을 위해 `NOLOGGING`을 사용하는 단계를 완전히 배제하고, 기본 `LOGGING` 모드로 작업을 진행합니다.**

#### **Reorg 후 반드시 해야 할 3가지 후속 작업**

테이블과 인덱스를 물리적으로 재구성하는 것만으로는 충분하지 않습니다. 작업의 완성도를 높이고 성능 향상 효과를 극대화하려면 다음 세 가지 작업이 필수적입니다.

1.  **Unusable 인덱스 체크**: `ALTER TABLE ... MOVE` 작업은 관련 인덱스를 `UNUSABLE` (사용 불가) 상태로 만듭니다. 이후 `ALTER INDEX ... REBUILD`를 수행하지만, 이 과정이 여러 이유로 실패할 수 있습니다. 만약 `UNUSABLE` 인덱스가 하나라도 남아있다면, 해당 인덱스를 이용하는 모든 SQL문이 오류를 일으키므로, 작업 마지막에 반드시 모든 인덱스가 `VALID` 상태인지 확인해야 합니다.

2.  **Invalid 객체 체크**: 테이블 재구성과 같은 대규모 DDL(Data Definition Language) 작업은 드물게 관련 프로시저, 뷰, 함수 등을 `INVALID` (무효) 상태로 만들 수 있습니다. 이런 객체들은 다음 번 실행 시 자동으로 재컴파일되기도 하지만, 의존성 문제로 계속 `INVALID` 상태에 머무를 수도 있습니다. 따라서 작업 후 `INVALID` 객체가 있는지 확인하여 조치하는 것이 안전합니다.

3.  **통계 정보 재수집**: 이것이 가장 중요합니다. Oracle 옵티마이저는 통계 정보를 기반으로 SQL 실행 계획을 수립합니다. Reorg 작업은 데이터의 물리적 위치(`ROWID`), 데이터 블록의 밀도, 데이터의 정렬 상태(Clustering Factor) 등 통계 정보와 관련된 거의 모든 것을 바꾸어 버립니다. 따라서 Reorg 직후에 `DBMS_STATS.GATHER_SCHEMA_STATS`를 실행하여 최신 상태의 통계 정보를 다시 수집해야만, 옵티마이저가 최적의 실행 계획을 수립하여 성능 향상 효과를 온전히 누릴 수 있습니다.

#### **우리의 새로운 상세 계획**

위의 후속 작업들을 포함하여, 우리의 계획은 다음과 같이 4단계로 구성됩니다.

*   **1단계: 사전 체크**: `reorg_pre_check.sql`로 DB 상태 점검.
*   **2단계: 사전 백업**: RMAN으로 만일의 사태 대비.
*   **3단계: 실행 및 검증**: `reorg_execute.sh`를 실행. 이 스크립트는 이제 다음 작업을 순차적으로 모두 수행합니다.
    *   `ALTER TABLE ... MOVE` (테이블 재구성)
    *   `ALTER INDEX ... REBUILD` (인덱스 재구성)
    *   **Unusable 인덱스 확인 (검증)**
    *   **Invalid 객체 확인 (검증)**
    *   **스키마 통계 수집 (최적화)**
*   **4단계: 후속 백업**: 깨끗해진 DB를 최종 백업.

### **Part 3. 코드 분석: 스크립트는 무엇을 하는가?**

이제 각 파일의 코드를 한 줄 한 줄 뜯어보며 구체적으로 무엇을 하는지 알아봅시다.

#### **1. `reorg_pre_check.sql`**
이 스크립트는 데이터베이스의 시스템 뷰(`V$`로 시작)와 데이터 딕셔너리 뷰(`DBA_`로 시작)를 조회하여 현재 상태를 보여줍니다.

*   `SELECT ... FROM V$PARAMETER WHERE NAME IN ('cpu_count', ...)`: `cpu_count` 같은 중요 시스템 설정 값을 보여줍니다.
*   `SELECT ... FROM V$OSSTAT ...`: OS 수준의 CPU 사용량 정보를 보여줍니다.
*   `SELECT ... FROM DBA_DATA_FILES, DBA_UNDO_EXTENTS ...`: Undo 테이블스페이스의 총량과 사용량을 계산해서 보여줍니다.
*   `SELECT ... FROM DBA_TEMP_FILES, V$TEMP_SPACE_HEADER ...`: 임시 테이블스페이스의 여유 공간을 보여줍니다.
*   `SELECT ... FROM V$RECOVERY_FILE_DEST`: 아카이브 로그가 저장되는 공간의 사용률을 보여줍니다.
*   `SELECT ... FROM V$PGASTAT, V$PGA_TARGET_ADVICE`: 병렬 작업에 사용될 메모리(PGA)의 현재 상태와 효율성을 보여줍니다.

#### **2. `reorg_execute.sh`**
이 셸 스크립트는 전체 Reorg 과정의 지휘자(Orchestrator)이며, 이제 더 많은 임무를 수행합니다.

*   **상단 설정**: `ORACLE_SID`, `ORACLE_HOME`, 접속 정보, 병렬 처리 수준(`DOP`) 등 실행 환경을 설정합니다.
*   **Helper 함수**: SQL 실행을 위한 함수들을 정의합니다.
*   **테이블/인덱스 목록 생성**: 재구성할 대상 목록을 동적으로 생성합니다.
*   **테이블 재구성 (병렬 처리)**: `ALTER TABLE ... MOVE`를 병렬로 실행합니다.
*   **인덱스 재빌드 (병렬 처리)**: `ALTER INDEX ... REBUILD`를 병렬로 실행합니다.
*   **인덱스 상태 검증 (추가된 기능)**: 스크립트는 인덱스 재빌드 후 `DBA_INDEXES`를 조회하여 `UNUSABLE` 상태인 인덱스가 있는지 확인합니다. 만약 하나라도 발견되면, 스크립트는 에러를 출력하고 즉시 중단하여 관리자가 문제를 인지하고 조치하도록 합니다.
*   **객체 상태 검증 (추가된 기능)**: `DBA_OBJECTS`를 조회하여 스키마 내에 `INVALID` 상태인 객체가 있는지 확인하고, 발견되면 경고 메시지와 함께 목록을 출력합니다.
*   **통계 수집 (추가된 기능)**: 모든 물리적인 작업이 끝난 후, `DBMS_STATS.GATHER_SCHEMA_STATS` 프로시저를 호출하여 스키마 전체의 통계 정보를 최신 상태로 업데이트합니다.

### **결론**

테이블 재구성은 데이터베이스의 건강을 유지하는 중요한 작업입니다. 하지만 강력한 만큼 시스템에 큰 부하를 주고, 잘못 실행하면 위험할 수 있습니다. 따라서 오늘 배운 것처럼, **명확한 이론적 이해**를 바탕으로 **체계적인 계획**을 세우고, **각 단계의 의미를 아는 것**이 무엇보다 중요합니다.

특히, 작업 속도보다는 **데이터의 안정성과 복구 가능성을 항상 최우선으로 고려**해야 합니다. `NOLOGGING`과 같은 위험한 옵션의 사용은 매우 신중해야 하며, Data Guard와 같은 고가용성 환경에서는 절대적으로 피해야 합니다. **마지막으로, 성공적인 Reorg는 통계 정보 수집과 결과 검증으로 마무리된다는 점**을 꼭 기억해야 합니다.

참고로, 실제 운영 환경에서는 이처럼 서비스를 중단하고 진행하는 '오프라인' 방식 외에, 서비스 중단 없이 재구성을 수행하는 '온라인' 방식(`DBMS_REDEFINITION` 패키지 사용)도 있습니다. 이 내용은 다음 학습 목표로 삼아보는 것도 좋을 것입니다.


### **SHIRINK가 아닌 ALTER TABLE을 선택한 이유**


인덱스 관리 (Index Rebuild 유무)

MOVE: 테이블의 ROWID가 통째로 바뀌므로 모든 관련 인덱스가 UNUSABLE 상태가 되어 반드시 REBUILD해야 합니다.

SHRINK: 인덱스 자체를 자동으로 관리해주지만, 데이터 이동 과정에서 인덱스 리프 노드에 대한 잦은 분할(Split)과 삽입이 발생하여 인덱스 내부의 파편화가 오히려 심해질 수 있습니다.

성능 및 부하 (Performance Overhead)

SHRINK는 개별 Row 단위로 INSERT와 DELETE를 수행하는 것과 유사한 내부 메커니즘을 가집니다. 따라서 대량의 데이터를 처리할 때 MOVE 방식보다 훨씬 오래 걸리고, Undo 및 Redo 로그 발생량이 압도적으로 많습니다.

데이터 압축 (Compression) 제약

SHRINK는 BASIC 압축(Direct Path Load 방식)이 적용된 테이블에는 사용할 수 없습니다. 반면 MOVE 방식은 데이터를 새로 쓰면서 COMPRESS 옵션을 통해 압축 효율을 극대화할 수 있습니다.

Row Chaining 및 Migration 해결 능력

MOVE는 데이터를 처음부터 다시 쓰기 때문에 Row Chaining이나 Migration을 완벽하게 해소합니다. SHRINK는 공간을 모으는 데 집중할 뿐, 블록 내부의 근본적인 저장 구조 최적화 측면에서는 MOVE보다 효율이 떨어질 수 있습니다.

기능적 제한

앞서 언급했듯이 Cluster Table, Long Column 등이 포함된 경우 SHRINK 자체가 불가능합니다. IOT나 파티션 테이블도 특정 상황에서는 MOVE를 통한 물리적 재배치가 더 안정적일 때가 많습니다.
