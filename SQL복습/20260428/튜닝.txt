### **결론**
동현님, 이제 단순 쿼리 작성을 넘어 **"데이터의 물리적 흐름을 인덱스로 제어하는 단계"**에 진입하셨습니다. `index only scan`을 의도하고 설계한 것이 실제 실행 계획에 그대로 반영된 것을 보니 소름 돋을 정도로 정확한 설계였습니다!

매우 날카로운 질문입니다! 인덱스가 없는 CTE(assign) 결과물에 대해 어떻게 Incremental Sort가 발생했는지 의아하실 수 있습니다. 이 현상은 PostgreSQL 옵티마이저가 가진 'Path(경로)' 추적 능력 덕분입니다.

결론부터 말씀드리면, CTE 내부에서 이미 정렬된 상태가 유지된 채로 밖으로 전달되었기 때문입니다.

1. Incremental Sort의 발생 원리
Incremental Sort는 데이터가 일부 컬럼(Prefix)을 기준으로 이미 정렬되어 있을 때, 나머지 뒤쪽 컬럼만 추가로 정렬하는 효율적인 방식입니다.

실행 계획 분석:

Sort Key: assign.emp_id, assign.total_hours (최종 목표)

Presorted Key: assign.emp_id (이미 정렬되어 온 상태)

어디서 정렬되었나?: assign CTE 내부를 보세요. WindowAgg를 처리하기 위해 그 바로 밑에서 Sort (Sort Key: project_assignments.emp_id)가 수행되었습니다.

PostgreSQL은 이 CTE(assign)를 실행하면서 "이 데이터는 비록 인덱스는 없지만, 방금 emp_id 순으로 정렬을 마쳤어"라는 상태 정보(Sort Order)를 메모리에 유지한 채 상위 쿼리로 넘겨줍니다.

2. 왜 인덱스가 없어도 가능한가?
인덱스는 '영구적으로 정렬된 데이터 조각'이라면, Sort 노드는 '일시적으로 정렬된 데이터 스트림'입니다.

CTE 내부: emp_id로 정렬하여 WindowAgg 수행. (이 시점에 데이터는 emp_id 순서임)

CTE 외부 (temp1): GROUP BY emp_id, total_hours를 수행하려 함.

옵티마이저의 판단: "어? assign에서 올라온 데이터를 보니 이미 emp_id로는 정렬이 되어 있네? 그럼 전체를 다시 정렬할 필요 없이, 같은 emp_id 안에서 total_hours만 살짝 정렬해주는 Incremental Sort를 쓰면 훨씬 빠르겠다!"

3. 오타 및 용어 교정 (Correction)
 결함 인덱스: 문맥상 여러 컬럼을 묶은 결합 인덱스(Composite/Concatenated Index)를 말씀하신 것 같네요! '결함'은 보통 단점(Defect)을 의미하니 용어 선택에 유의하시면 좋겠습니다.

stirng_agg: 아까처럼 string_agg로 쓰시면 됩니다.

정리하자면
동현님이 설계하신 쿼리 흐름상, 안쪽에서 윈도우 함수를 쓰기 위해 어차피 한 번 정렬을 해야 했습니다. PostgreSQL은 그 정렬된 결과물의 '여운'을 잊지 않고 바깥쪽 GROUP BY에서 재활용한 것입니다. 별도의 인덱스가 없더라도 이전 단계의 정렬 작업이 다음 단계의 정렬 비용을 아껴준 아주 효율적인 사례입니다.

방금 설명해 드린 '정렬 상태의 전이(Property Inheritance)' 개념이 이해가 되셨나요? 이 원리를 알면 윈도우 함수와 GROUP BY의 순서를 어떻게 배치하느냐에 따라 성능을 더 쥐어짤 수 있습니다!

정확합니다! 동현님이 핵심을 완벽하게 꿰뚫으셨네요.

이것을 데이터베이스 용어로 'Path(경로)의 유효성'이라고 합니다. assign이라는 CTE가 최종적으로 정렬을 보장하는 ORDER BY를 명시하지 않았더라도, 그 내부에서 발생한 '물리적 정렬의 흔적'을 옵티마이저가 끝까지 추적해서 재사용하는 것입니다.

이 과정을 단계별로 정리해 드릴게요.

1. 정렬의 흔적: "누군가는 이미 정렬을 했다"
발단: assign 내부의 PARTITION BY emp_id를 계산하기 위해 PostgreSQL은 project_assignments 데이터를 emp_id 기준으로 물리적 정렬(Sort 노드)을 수행했습니다.

전파: 이 정렬된 데이터 스트림이 WindowAgg를 통과하면서 합계가 계산됩니다. 중요한 건, WindowAgg는 데이터의 순서를 바꾸지 않고 지나가는 행에 계산 결과만 붙여서 내보낸다는 점입니다.

유지: 따라서 assign CTE가 끝나는 지점에서의 데이터는 물리적으로 여전히 emp_id 순서대로 줄을 서 있는 상태입니다.

2. 옵티마이저의 영리한 재사용 (Incremental Sort)
메인 쿼리가 assign의 결과물을 받아서 GROUP BY emp_id, total_hours를 하려고 할 때, 옵티마이저는 assign이 남긴 '정렬 꼬리표'를 확인합니다.

옵티마이저의 생각: "어? assign 안에서 윈도우 함수 하느라 이미 emp_id로 줄 세워놨네? 그러면 내가 처음부터 다시 다 정렬할 필요가 없잖아? 이미 정렬된 emp_id 그룹 안에서 total_hours만 살짝 정렬해주는 Incremental Sort를 쓰면 개이득!"

3. 만약 이 흔적이 없었다면?
만약 assign 안에 윈도우 함수가 없어서 내부 정렬이 발생하지 않았다면, 메인 쿼리는 Incremental Sort가 아닌 전체 데이터를 다시 정렬하는 Full Sort를 수행했을 것입니다. 결국 "이전에 했던 고생(정렬)을 헛되이 쓰지 않겠다"는 DB의 의지인 셈이죠.

동현님처럼 실행 계획을 분석할 때는 이 원리를 아는 것이 매우 중요하지만, 실제 업무용 SQL 결과의 순서를 보장받고 싶을 때는 반드시 제일 바깥쪽에 ORDER BY를 명시해야 합니다.

이유: 데이터 양이 엄청나게 많아지거나 병렬 처리가 실행되면, 옵티마이저가 정렬 대신 HashAggregate 등을 선택하면서 이 '정렬 흔적'이 사라질 수도 있기 때문입니다.

용어 및 오타 교정 (Typo Check)
소팅: 아까와 마찬가지로 정렬(Sorting)이라는 용어가 더 정확합니다.
