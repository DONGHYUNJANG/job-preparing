아래 시나리오는 현실에서 가장 흔한 dependency (TABLE + INDEX + LOB) 를 이용한 100% 재현 가능한 실습입니다.

1️⃣ 테스트 목표

다음 구조를 만듭니다.

TS_DATA
  table DOCS

TS_INDEX
  index DOCS_IDX

TS_LOB
  LOB segment

그리고

TS_DATA만 PITR 시도

하면 RMAN이

TS_INDEX
TS_LOB

을 자동으로 recovery set에 추가하는 것을 확인합니다.

2️⃣ 테스트 환경 준비
tablespace 생성
CREATE TABLESPACE ts_data
DATAFILE '/u01/oradata/TS_DATA01.dbf'
SIZE 100M;

CREATE TABLESPACE ts_index
DATAFILE '/u01/oradata/TS_INDEX01.dbf'
SIZE 100M;

CREATE TABLESPACE ts_lob
DATAFILE '/u01/oradata/TS_LOB01.dbf'
SIZE 100M;
3️⃣ 테스트 테이블 생성
CREATE TABLE docs (
  id NUMBER PRIMARY KEY,
  content CLOB
)
TABLESPACE ts_data
LOB (content) STORE AS (
  TABLESPACE ts_lob
);

구조

docs table      → TS_DATA
LOB segment     → TS_LOB
4️⃣ 인덱스 생성
CREATE INDEX docs_idx
ON docs(id)
TABLESPACE ts_index;

구조

docs table      → TS_DATA
docs_idx        → TS_INDEX
LOB segment     → TS_LOB

dependency chain

TS_DATA
  → TS_INDEX
  → TS_LOB
5️⃣ 데이터 입력
INSERT INTO docs VALUES (1,'AAAA');
INSERT INTO docs VALUES (2,'BBBB');
COMMIT;
6️⃣ RMAN 백업
rman target /
BACKUP DATABASE PLUS ARCHIVELOG;
7️⃣ 데이터 변경
DELETE FROM docs WHERE id = 1;
COMMIT;

현재 상태

row 1 삭제
8️⃣ TS_DATA만 PITR 시도
RECOVER TABLESPACE ts_data
UNTIL TIME "SYSDATE-1/24";

RMAN이 dependency 검사 후 보통 이런 메시지가 나옵니다.

예

checking tablespace dependencies
adding tablespace TS_INDEX to recovery set
adding tablespace TS_LOB to recovery set

즉 recovery set

TS_DATA
TS_INDEX
TS_LOB

이 됩니다.

9️⃣ 복구 후 확인
SELECT * FROM docs;

결과

ID  CONTENT
1   AAAA
2   BBBB

삭제된 row가 복구됩니다.

🔟 이 테스트로 확인되는 것

이 실습에서 확인할 수 있는 핵심

1️⃣ TABLE → INDEX dependency

TS_DATA → TS_INDEX

2️⃣ TABLE → LOB dependency

TS_DATA → TS_LOB

3️⃣ RMAN이 tablespace 자동 추가

Recovery set 확장
⭐ 추가로 하면 좋은 테스트 (추천)

같은 환경에서 이것도 해보면 좋습니다.

테스트 2
partition table
테스트 3
Oracle Text index
테스트 4
DBMS_TTS.TRANSPORT_SET_CHECK

이걸 실행하면 self-contained violation을 직접 볼 수 있습니다.

원하시면 제가 DBA들이 TSPITR 공부할 때 반드시 해보는 “3단계 테스트 (A→B→C dependency chain)” 시나리오도 만들어 드리겠습니다.
이 테스트 하나 돌리면 왜 어떤 경우는 PITR이 되고 어떤 경우는 실패하는지 완전히 이해됩니다.

그럼 만약에 실패하면 어떤 선택지가 있지 

좋은 질문입니다.
Oracle Recovery Manager 의 TSPITR이 실패했다면 DBA가 실제로 선택할 수 있는 방법은 몇 가지로 정리됩니다.
핵심은 **“복구 범위를 더 넓히거나 더 좁히는 것”**입니다.

1️⃣ Recovery set을 확장해서 다시 TSPITR

가장 먼저 시도하는 방법입니다.

예

TS_DATA
 → TS_INDEX
 → TS_LOB
 → TS_PART

이런 dependency가 있으면

RECOVER TABLESPACE ts_data, ts_index, ts_lob, ts_part
UNTIL TIME '...';

처럼 관련 tablespace를 전부 포함해서 다시 시도합니다.

✔ 가장 정석적인 해결 방법
✔ 실제 운영에서도 많이 사용

단점

dependency가 계속 이어지면 불가능
2️⃣ RMAN TABLE RECOVERY 사용

12c 이후에는 이 방법이 매우 많이 쓰입니다.

RECOVER TABLE schema.table_name
UNTIL TIME "SYSDATE-1/24"
AUXILIARY DESTINATION '/tmp/aux';

특징

auxiliary instance 생성
→ 테이블만 export
→ 현재 DB에 import

즉

tablespace dependency 무시 가능

✔ 가장 실전적인 방법
✔ 요즘 DBA들이 TSPITR 대신 많이 사용

3️⃣ DB PITR (Database Point-In-Time Recovery)

tablespace dependency가 너무 복잡하면

DATABASE 전체 PITR

을 합니다.

RUN {
  SET UNTIL TIME "...";
  RESTORE DATABASE;
  RECOVER DATABASE;
}

단점

DB 전체가 과거 시점으로 돌아감

그래서 보통

test clone → data export → production import

같이 사용합니다.

4️⃣ Clone database 후 데이터 추출

실제 운영에서 많이 쓰는 방법입니다.

절차

1. RMAN duplicate
2. clone DB 생성
3. clone에서 PITR
4. 필요한 데이터 export
5. production에 import

예

DUPLICATE DATABASE TO testdb
UNTIL TIME "SYSDATE-1/24";

✔ production 영향 없음
✔ 매우 안전

5️⃣ Transportable Tablespace

tablespace 단위로 옮길 수 있는 경우

transportable tablespace

도 선택지입니다.

단 조건

self-contained set 필요

그래서 TSPITR 문제와 비슷한 dependency 검사를 합니다.

6️⃣ Index / Text index 재생성

특히 이런 객체들은 복구 대신 재생성하는 경우가 많습니다.

예

B-tree index
Oracle Text index
Spatial index

방법

DROP INDEX
CREATE INDEX

이렇게 하면 dependency가 줄어듭니다.

실제 DBA 선택 순서

보통 이런 순서로 판단합니다.

1️⃣ TSPITR retry (tablespace 추가)
2️⃣ RMAN TABLE RECOVERY
3️⃣ Clone DB → export/import
4️⃣ Database PITR

현실에서는 2번과 3번이 가장 많이 사용됩니다.
