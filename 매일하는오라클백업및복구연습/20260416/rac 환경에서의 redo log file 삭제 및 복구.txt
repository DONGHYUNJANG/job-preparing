current log 파일 삭제 후 가능한곳 까지만 복구 (SCN기반)

복구 순서 요약
srvctl stop database : 전체 DB 정지
STARTUP MOUNT : MOUNT까지만 기동
@log : 상태 확인, INACTIVE 여부 확인
DROP LOGFILE GROUP N : 손상된 그룹 제거
ADD LOGFILE THREAD N GROUP N : 새 그룹 재생성
ALTER DATABASE OPEN : DB 오픈
ALTER SYSTEM SWITCH LOGFILE : 새 그룹 활성화

방법 1. CLEAR 명령어로 한 방에 해결 (권장)
해당 그룹에 살아있는 멤버가 하나라도 있다면, 이 명령어가 가장 쉽고 빠릅니다.

SQL
SQL> ALTER DATABASE CLEAR LOGFILE GROUP 2;
작동 원리: 이 명령을 날리면 오라클이 해당 그룹(Group 2)의 모든 멤버를 물리적으로 새로 생성하고 초기화합니다.

장점: 깨진 파일은 알아서 지우고(혹은 덮어쓰고) 건강한 상태로 다시 만들어줍니다. 질문하신 "다음 사이클 때 동기화"를 기다릴 필요 없이 즉시 새 파일로 준비됩니다.

1. CLEAR LOGFILE 
ALTER DATABASE CLEAR LOGFILE GROUP [그룹번호];
파일 재생성: OS에서 삭제된 파일을 오라클이 직접 다시 만들어줍니다.

상태 초기화: CURRENT든 ACTIVE든 묻지도 따지지도 않고 깨끗한 상태로 세팅합니다.

DB 오픈 가능: 이 명령으로 유실된 파일을 살려내면 즉시 ALTER DATABASE OPEN;이 가능해집니다.

2. ALTER SYSTEM ARCHIVE LOG CURRENT; 후 Drop (될지 안될지 모르고 비권장이라고 한다.)

## 가장 최신의 백업본이 SCN 3291901 시점보다 늦게 만들어진 백업본뿐이라서 에러가 발생한다.
왜? 

1. 원인: 백업 시점보다 더 과거로 갈 수는 없다
RMAN의 RESTORE UNTIL SCN은 다음 규칙을 따릅니다.

성공 조건: 데이터파일 1번부터 21번까지 모두 SCN 3291901보다 작은(과거의) SCN을 가진 백업본이 존재해야 함.

현재 문제: 지금 가지고 계신 백업본들의 SCN이 3291901보다 큰(미래인) 것 같습니다.

예시:

내가 가진 백업본의 SCN이 3300000이라고 칩시다.

아까 시도했던 최신 시점(예: 3310000)으로의 복구는 3300000 백업본을 가져다가 로그를 더하면 되니까 성공합니다.

하지만 3291901로 돌아가고 싶다면? 3300000 백업본은 이미 그보다 미래의 데이터라 쓸 수 없습니다. 3291901보다 더 옛날 백업본이 필요한데, 그게 지금 RMAN이 못 찾겠다고 아우성치는 겁니다

1. UNDO가 있는데 왜 못 돌아가나요?
오라클에서 UNDO 데이터의 주 목적은 **롤백(Rollback)**입니다. 하지만 복구(Recovery) 작업은 결이 조금 다릅니다.

UNDO의 역할: "작업이 진행 중인(Active)" 트랜잭션을 취소할 때 사용합니다.

RECOVER의 원리: 데이터파일에 로그(Redo)를 **덧칠해서 미래로만 전진(Forward)**하는 방식입니다.

문제의 지점: 아까 RECOVER를 하다가 이미 SCN 3309339까지 데이터파일을 업데이트해버렸죠? 오라클 엔진 입장에서 이 파일은 이제 "3309339 버전"입니다.

오라클의 한계: 여기서 "3291901 버전"으로 가고 싶을 때, UNDO를 써서 파일을 깎아내려가는 기능은 일반적인 RECOVER 명령에는 없습니다. (이걸 해주는 기능은 'Flashback Database'라는 별도의 기능뿐입니다.)
