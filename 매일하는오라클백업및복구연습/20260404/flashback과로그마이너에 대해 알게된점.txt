Flashback On을 할 필요가 없습니다.

1. Flashback Database ON이 필요 없는 경우 (기본 기능)
우리가 흔히 쓰는 행 단위 복구 기능들은 데이터베이스를 켤 때 별도의 ON 설정이 필요 없습니다.

Flashback Query: (언두 사용) 그냥 바로 사용 가능.

Flashback Drop: (휴지통 사용) DROP TABLE... 하면 자동으로 휴지통(Recyclebin)으로 들어가며, 바로 복구 가능.

Flashback Table: (언두 사용) 테이블의 ROW MOVEMENT만 활성화하면 바로 사용 가능.

2. ALTER DATABASE FLASHBACK ON;이 꼭 필요한 경우
질문하신 ON 설정은 DB 전체를 과거로 돌리는 '플래시백 데이터베이스' 기능을 쓸 때만 필요합니다.

용도: DB 전체를 1시간 전으로 통째로 되감기 할 때.

설정 조건: 1.  DB가 Archivelog Mode여야 함.
2.  **FRA(Fast Recovery Area)**가 설정되어 있어야 함.
3.  MOUNT 단계에서 ALTER DATABASE FLASHBACK ON; 실행.

3. "그럼 플래시백 쿼리는 설정할 게 아예 없나?"
ON은 안 해도 되지만, **'언두(Undo) 파라미터'**가 중요합니다. 플래시백 쿼리는 언두 데이터를 빌려 쓰기 때문이죠.

UNDO_RETENTION: "언두 데이터를 얼마나 오래 보관할 것인가?" (초 단위)

예를 들어 이 값이 900(15분)이면, 15분 전 데이터까지는 플래시백 쿼리로 볼 확률이 높지만, 그 이상 지나면 장담할 수 없습니다.

Tablespace 크기: 언두 테이블스페이스가 너무 작으면 보관 주기가 지나지 않았어도 새 데이터가 옛날 데이터를 덮어써 버립니다.

💡 요약하자면!


방금 실수로 지운 데이터 찾기 (Query): 설정 필요 없음. 그냥 AS OF TIMESTAMP 쓰면 됨.

DB를 통째로 과거로 돌리기 (Database): FLASHBACK ON 필수 + 유료 옵션(EE).

기능,사용하는 데이터,비용,복구 단위
Flashback Query,Undo,무료,행(Row) 단위 조회
Flashback Table,Undo,무료(EE),테이블 통째로 복구
Flashback Drop,Recycle Bin,무료,삭제된 테이블 복구 (PURGE 전까지)
Flashback Database,Flashback Logs,유료(EE),DB 전체 복구

1. 특정 테이블의 DELETE 문만 추출하기
로그마이너를 시작한 상태에서 아래와 같이 쿼리를 날리면 됩니다.

SQL
SELECT 
    SCN, 
    TIMESTAMP, 
    SQL_REDO,   -- 실제 실행된 DELETE 문
    SQL_UNDO    -- 복구에 필요한 INSERT 문
FROM V$LOGMNR_CONTENTS
WHERE OPERATION = 'DELETE'              -- 작업 종류 필터링
  AND TABLE_NAME = 'EMP'                -- 특정 테이블 지정
  AND SEG_OWNER = 'SCOTT';              -- 소유자 지정 (권장)
2. 추출한 SQL을 파일이나 테이블로 저장하기
화면에 출력만 해서는 양이 많을 때 관리가 안 되죠. 보통은 아래 두 가지 방법을 씁니다.

방법 A: 임시 테이블에 담기 (가장 추천)
나중에 엑셀로 뽑거나 하나씩 실행해보기 가장 편합니다.

SQL
CREATE TABLE MY_RECOVERY_LOGS AS
SELECT SQL_UNDO 
FROM V$LOGMNR_CONTENTS
WHERE OPERATION = 'DELETE' AND TABLE_NAME = 'EMP';
방법 B: 스풀(SPOOL) 기능을 이용해 텍스트 파일로 저장
SQL*Plus 환경이라면 파일로 바로 구울 수 있습니다.

SQL
SET HEADING OFF FEEDBACK OFF PAGESIZE 0 TRIMSPOOL ON
SPOOL recovery_script.sql
SELECT SQL_UNDO || ';' FROM V$LOGMNR_CONTENTS 
WHERE OPERATION = 'DELETE' AND TABLE_NAME = 'EMP';
SPOOL OFF
3. 왜 SQL_UNDO가 더 중요할까?
질문하신 것처럼 DELETE 문(SQL_REDO)만 뽑는 것도 분석용으로는 좋지만, 복구가 목적이라면 SQL_UNDO를 뽑아야 합니다.

SQL_REDO: DELETE FROM EMP WHERE EMPNO = 7788... (실수 내용 확인용)

SQL_UNDO: INSERT INTO EMP (EMPNO, ENAME...) VALUES (7788, 'SCOTT'...) (복구용)

로그마이너는 지워진 데이터의 모든 컬럼 값을 알고 있기 때문에, SQL_UNDO에는 아주 완벽한 형태의 INSERT 문이 만들어져 있습니다. 그냥 복사해서 붙여넣기만 하면 끝이죠.

장애 발생 시 "진짜" 골든타임 행동 강령
데이터를 날렸다는 보고를 받는 순간, 당황해서 Restore부터 하지 마시고 아래 순서로 움직이세요.

아카이빙 강제 실행 (최우선):
ALTER SYSTEM ARCHIVE LOG CURRENT;
이걸 하면 현재 온라인 리두에 있던 '실수 기록'이 안전하게 아카이브 파일로 복사됩니다. 이제 리두 파일이 덮어씌워질 걱정은 끝입니다.

현재 SCN 확인:
SELECT CURRENT_SCN FROM V$DATABASE;
지금 이 시점의 번호를 적어두세요. 복구의 기준점이 됩니다.

로그마이너 투입:
아카이브된 파일에서 SQL_UNDO를 뽑아봅니다. 여기서 해결되면 DB를 내릴 필요도, 리셋로그를 할 필요도 없습니다.
