# db file sequential read and db file scattered read

## **1. db file sequential read (Single Block I/O)**

이 이벤트는 세션이 **한 번에 하나의 데이터 블록**을 메모리(Buffer Cache)로 읽어 들일 때 발생합니다.

- **발생 상황:** 주로 **인덱스**를 통해 데이터를 조회할 때 발생합니다. 인덱스 리프 블록을 읽고, 그 주소(ROWID)를 따라가서 테이블의 특정 블록 하나를 읽는 과정이 '순차적(Sequential)'으로 일어나기 때문입니다.
- **특징:** 대기 시간이 짧은 것이 정상입니다. 만약 이 이벤트의 대기 시간이 길어진다면, 디스크 자체의 성능 문제(I/O Bottleneck)이거나 버퍼 캐시가 너무 작아 반복적으로 디스크를 읽는 상황일 수 있습니다.

## **2. db file scattered read (Multi Block I/O)**

이 이벤트는 세션이 **한 번에 여러 개의 데이터 블록**을 메모리로 읽어 들일 때 발생합니다.

- **발생 상황:** 주로 **Full Table Scan**이나 **Index Fast Full Scan**을 할 때 나타납니다. 오라클은 효율을 높이기 위해 여러 블록을 한꺼번에 읽어서 메모리 여기저기에 '흩뿌려(Scattered)' 저장합니다.
- **특징:** 한 번에 많이 읽기 때문에 `sequential read`보다 한 번의 대기 시간(Latency)은 길 수 있지만, 전체 데이터를 읽는 효율은 더 좋을 수 있습니다. 하지만 튜닝 관점에서는 불필요하게 큰 테이블을 전체 스캔하고 있지는 않은지 점검해 봐야 합니다.

| **이벤트명** | **읽기 방식** | **주요 발생 원인** | **비고** |
| --- | --- | --- | --- |
| **sequential read** | Single Block | 인덱스 스캔, ROWID 추출 | 인덱스 효율성 확인 필요 |
| **scattered read** | Multi Block | Full Table Scan | 인덱스 누락 또는 Full Scan 적절성 확인 |

> **db file sequential read 가 많이 일어나는 sql 특정**
> 

SELECT sql_id, COUNT(*)
FROM DBA_HIST_ACTIVE_SESS_HISTORY
WHERE event = 'db file sequential read'
-- 특정 기간을 지정하고 싶을 때 (예: 최근 24시간)
AND sample_time > SYSDATE - 1
GROUP BY sql_id
ORDER BY 2 DESC;

## 📑 개념 설명: ASH 샘플링과 카운트의 관계

CPU가 1,000개의 블록을 가져오라고 시켰을 때, 오라클 내부에서는 다음과 같은 일이 벌어집니다.

1. **명령 전달**: CPU는 디스크 컨트롤러에게 "1번 블록 가져와"라고 시킵니다.
2. **대기 상태**: CPU는 디스크가 응답할 때까지 이 세션의 상태를 `db file sequential read` 대기 상태로 표시하고 다른 일을 하거나 기다립니다.
3. **샘플링 (ASH)**: 바로 이 순간, 1초마다 돌아가는 ASH 감시자가 "지금 이 세션 뭐해?"라고 물으면 세션은 "나 지금 1번 블록 기다려"라고 대답합니다. → **카운트 +1**
4. **반복**: 1번 블록이 오면 바로 "2번 블록 가져와"라고 시킵니다. 이 과정이 1,000번 반복되는 동안 ASH 감시자가 올 때마다 아직도 블록을 기다리고 있다면 계속 찍히는 것입니다.

## 🛠️ 문제 해설: 카운트가 올라가는 두 가지 시나리오

사용자님이 말씀하신 "카운트가 올라간다"는 상황은 크게 두 가지 의미를 내포합니다.

### 1. 양이 너무 많을 때 (비효율적인 SQL)

- 블록 1개를 가져오는 데 0.01초밖에 안 걸린다고 가정해 봅시다.
- 하지만 읽어야 할 블록이 **1,000,000개**라면? 전체 작업 시간은 10,000초가 됩니다.
- ASH 감시자는 10,000번 방문하는 동안 거의 매번 이 세션이 디스크를 기다리는 모습을 목격하게 됩니다. → **카운트 폭발**

### 2. 속도가 너무 느릴 때 (I/O 병목)

- 읽어야 할 블록은 단 **10개**뿐입니다.
- 그런데 디스크가 너무 느려서 블록 1개를 가져오는 데 10초가 걸린다고 가정해 봅시다.
- ASH 감시자는 100초 동안 방문하면서 이 세션을 계속 목격합니다. → **카운트 상승**

## 📑 개념 설명: 대기 이벤트의 샘플링 메커니즘

네, 맞습니다! 사용자께서 이해하신 **"스냅샷(샘플링)에 찍힌 횟수 = 대기 시간의 총합"**이라는 원리는 오라클의 거의 모든 대기 이벤트 분석에 동일하게 적용됩니다.

오라클의 성능 관리 철학은 **"사용자가 요청을 보낸 후 결과를 받을 때까지의 전체 시간(Response Time)"**을 분석하는 것입니다. 이 시간은 아래와 같은 공식으로 표현됩니다.

$$Response\ Time = Service\ Time(CPU\ Usage) + Wait\ Time(Enqueued/IO/Etc.)$$

ASH(Active Session History)는 이 공식에서 세션이 어떤 '상태'에 머물러 있는지를 초 단위로 기록하여, 어디서 시간이 가장 많이 소요되었는지 역추적할 수 있게 해줍니다.

## 🛠️ 문제 해설: 다른 대기 이벤트들의 샘플링 예시

`db file sequential read` 외에 다른 주요 이벤트들도 같은 방식으로 샘플링되어 카운트됩니다.

### 1. `enq: TX - row lock contention` (락 대기)

- **상황**: A 사용자가 특정 로우를 수정 중인데, B 사용자가 같은 로우를 수정하려고 시도합니다.
- **샘플링**: B 세션은 CPU를 내려놓고 '기다림' 상태로 들어갑니다. ASH가 1초마다 지나가면서 B를 볼 때마다 "너 뭐해?"라고 물으면, B는 "나 락 풀리길 기다려"라고 대답합니다.
- **분석**: 만약 이 이벤트의 카운트가 3600이라면, 누군가 1시간(3600초) 동안 락을 잡고 있어서 다른 세션들이 그만큼 멈춰 있었다는 뜻입니다.

### 2. `log file sync` (커밋 대기)

- **상황**: 사용자가 `COMMIT`을 날렸는데, LGWR(Log Writer) 프로세스가 리두 로그를 디스크에 다 적을 때까지 기다려야 합니다.
- **샘플링**: 디스크 쓰기가 느리면 ASH 샘플링 순간에 이 "커밋 대기" 상태가 자주 포착됩니다.
- **분석**: 카운트가 높다면 "우리 시스템은 커밋 처리가 너무 느려서 사용자들이 불필요하게 대기하고 있다"고 판단합니다.

### 3. `On CPU` (대기가 아닌 상태)

- **상황**: 세션이 대기 이벤트 없이 열심히 연산 중입니다.
- **샘플링**: ASH가 방문했을 때 `event` 컬럼이 비어있거나(NULL) `On CPU`라고 되어 있습니다.
- **분석**: 이 카운트가 높다면 대기 문제가 아니라, SQL 자체가 복잡해서 계산량이 너무 많거나 인덱스 없이 메모리 내에서 너무 많은 데이터를 뒤지고 있는 것입니다.

---

## 💡 요약 및 포인트

1. **샘플링은 확률입니다**: 짧은 대기는 안 찍힐 수도 있지만, **길거나 잦은 대기**는 반드시 ASH에 많이 찍히게 되어 있습니다.
2. **병목 지점 파악**: ASH 카운트가 가장 높은 이벤트를 해결하는 것이 전체 시스템 성능을 올리는 가장 빠른 길입니다.
3. **Top Wait Events**: AWR 리포트나 ASH 분석에서 상위에 랭크된 이벤트들이 바로 사용자님이 말씀하신 "스냅샷에 가장 많이 걸린 범인들"입니다.

## 📑 개념 설명: 왜 실행 계획을 봐야 하는가?

실행 계획(`Execution Plan`)은 오라클 옵티마이저가 데이터를 가져오기 위해 선택한 **최적의 경로**입니다. ASH에서 확인한 대기 이벤트와 실행 계획을 연결하면 문제의 원인이 명확해집니다.

- **ASH 결과**: `db file sequential read` 카운트가 매우 높음
- **실행 계획 확인**: `INDEX RANGE SCAN` 후 `TABLE ACCESS BY INDEX ROWID`가 나타남
- **결론**: "아, 인덱스를 타긴 하는데 읽어야 할 블록이 너무 많아서 한 땀 한 땀 읽느라 대기가 발생했구나!" → **결합 인덱스 변경이나 Full Scan 유도 검토**

## 🛠️ 문제 해설: 실행 계획 분석의 흐름

보통 실무나 OCP 시험 관점에서는 아래와 같은 순서로 분석을 진행합니다.

### 1. SQL ID의 실행 계획 확인

먼저 문제가 된 SQL의 실행 계획을 메모리(또는 AWR)에서 불러옵니다.

SQL

```jsx
- 메모리에 있는 실행 계획 확인
SELECT  FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR('sql_id', NULL, 'ALLSTATS LAST'));
- 과거 이력(AWR)에 있는 실행 계획 확인
SELECT  FROM TABLE(DBMS_XPLAN.DISPLAY_AWR('sql_id'));
```

### 2. 대기 이벤트와 실행 단계 매칭

실행 계획의 각 단계(Operation) 중 어떤 부분에서 시간이 가장 많이 소요되었는지 체크합니다.

- **Full Table Scan**: 인덱스가 없어서 통째로 읽고 있는가? (`db file scattered read` 발생)
- **Nested Loops Join**: 조인 방식이 비효율적이라 반복 횟수가 너무 많은가?
- **Cartesian Product**: 조인 조건이 빠져서 데이터가 폭발하고 있는가?

### 3. 해결책 제시 (Tuning)

실행 계획에서 발견된 '비효율'을 제거합니다.

- **인덱스 추가/수정**: 필요한 데이터를 더 빠르게 찾도록 함
- **힌트(Hint) 사용**: 옵티마이저에게 더 좋은 경로를 강제함 (`/*+ INDEX(t ...) */` 등)
- **통계 정보 갱신**: 오라클이 데이터 양을 오해하고 있다면 최신 정보로 업데이트함
