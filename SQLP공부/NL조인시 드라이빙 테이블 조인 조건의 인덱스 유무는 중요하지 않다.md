결론부터 말씀드리면, 맞습니다! 완벽하게 정확한 명제입니다.

Nested Loops(NL) 조인이 일어날 때, 선행 테이블(Driving/Outer Table)의 조인 조건 컬럼에 인덱스가 있는지 없는지는 조인 속도와 매커니즘에 아무런 영향을 주지 않습니다.

반면에, 후행 테이블(Driven/Inner Table)의 조인 조건 컬럼 인덱스는 NL 조인의 생사를 결정할 만큼 절대적으로 중요합니다.

왜 드라이빙 테이블의 조인 조건 인덱스는 상관이 없는지, 그 이유를 뼛속까지 이해하실 수 있도록 구조적으로 풀어드리겠습니다.

---

## 1. 이유: 드라이빙 테이블은 조인 조건을 '비교'당하는 입장이기 때문

NL 조인의 내부 메커니즘을 2중 `for` 루프 문으로 다시 떠올려보면 쉽게 이해할 수 있습니다.

```text
// 1. 선행 테이블(Driving)을 먼저 읽음 (여기서는 조인 조건 인덱스가 필요 없음!)
for each row in Driving_Table 
{
    // 2. 읽어온 Driving 테이블의 조인 컬럼 값(X)을 상수로 취급하여
    //    후행 테이블(Driven)의 인덱스를 콕 집어 검색(Seek)함
    
    Search Driven_Table_Index WHERE Driven_Join_Column = Driving_Table.Join_Column(X);
}

```

* 드라이빙 테이블의 역할: 그냥 자기 테이블에 있는 데이터를 `WHERE` 절 조건대로 먼저 쭉 읽어내려가는(Scan) 역할입니다. 읽은 데이터 속에 들어있는 조인 컬럼 값(예: 사원번호 `10번`, `20번`)을 꺼내서 후행 테이블에 던져주는 주체일 뿐입니다.
* 던져주는 입장이다 보니, 정작 자기 자신의 조인 조건 컬럼에 인덱스가 있든 없든 데이터를 읽는 방식(`Full Table Scan`이든 다른 조건의 `Index Scan`이든)에는 아무런 영향을 주지 않습니다.

---

## 2. 그렇다면 드라이빙 테이블에 '진짜' 중요한 인덱스는 무엇일까?

드라이빙 테이블에서 정작 중요한 것은 조인 조건 컬럼이 아니라, `WHERE` 절에 걸려있는 일반 필터 조건 컬럼의 인덱스입니다.

```sql
SELECT *
FROM employees e -- Driving 테이블
INNER JOIN departments d -- Driven 테이블
    ON e.department_id = d.department_id -- (A) 조인 조건
WHERE e.job_id = 'IT_PROG'; -- (B) 일반 필터 조건

```

* (A) `e.department_id` 인덱스 (조인 조건): 필요 없습니다. 옵티마이저가 처음에 `employees` 테이블을 읽을 때 이 인덱스는 쳐다보지도 않습니다.
* (B) `e.job_id` 인덱스 (필터 조건): 매우 중요합니다. 이 인덱스가 있어야 `job_id = 'IT_PROG'`인 데이터만 선 필터링하여 드라이빙 건수를 최소한(예: 5건)으로 줄인 채 조인 루프에 진입할 수 있기 때문입니다.

---

## 3. 핵심 요약: NL 조인 인덱스 완벽 가이드

실무나 시험에서 NL 조인의 인덱스 유무를 판단할 때는 딱 이 두 가지만 기억하시면 됩니다.

1. 선행 테이블 (Driving / Outer)
* 조인 조건 컬럼 인덱스: 필요 없음 (무의미)
* 일반 필터 조건 컬럼 인덱스: 매우 중요 (드라이빙 로우 수를 줄여서 `cr` 폭발을 막는 생명줄)


2. 후행 테이블 (Driven / Inner)
* 조인 조건 컬럼 인덱스: 절대적으로 필수! (이게 없으면 드라이빙 테이블에서 넘어오는 건수만큼 후행 테이블을 Full Scan해야 하므로 쿼리가 멈춤)
* 일반 필터 조건 컬럼 인덱스: 있으면 좋지만, 조인 조건 인덱스 뒤에 결합 인덱스로 묶여있을 때 가장 효과적임.
