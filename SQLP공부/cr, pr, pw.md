오라클 실행 계획(Execution Plan)의 Trace 결과(SQL 트레이스나 `DBMS_XPLAN.DISPLAY_CURSOR` 등)에서 볼 수 있는 `cr`, `pr`, `pw`는 쿼리가 실행되는 동안 발생한 I/O(Input/Output)의 종류와 양을 나타내는 핵심 지표입니다.

이 지표들을 분석하면 쿼리가 왜 느린지, 메모리를 잘 쓰고 있는지, 아니면 디스크를 긁고 있는지 정확하게 진단할 수 있습니다. 각 용어의 의미와 해석 방법을 깔끔하게 정리해 드리겠습니다.

---

## 1. 세 가지 핵심 지표의 정의

### `cr` (Consistent Read) - 메모리 읽기 (논리적 I/O)

* 의미: 일관성 있는 읽기를 위해 메모리(Buffer Cache)에서 읽은 블록 수입니다.
* 특징: 오라클의 대원칙인 '읽기 일관성(Read Consistency)'을 보장하기 위해, 내가 쿼리를 시작한 시점 이후에 다른 세션에 의해 변경된 블록을 만나면 UNDO 세그먼트(또는 UNDO 블록)를 찾아가 변경 전 과거 데이터(CR Copy)를 조합해서 읽어옵니다.
* 해석: 이 값이 크다는 것은 쿼리가 처리하는 데이터의 양(Scanned Blocks) 자체가 많거나, 조인 루프(Loop)를 돌며 메모리를 덤벼드는 횟수가 많다는 뜻입니다.

### `pr` (Physical Read) - 디스크 읽기 (물리적 I/O)

* 의미: 필요한 데이터 블록이 메모리(Buffer Cache)에 없어서 디스크(Datafile)에서 직접 읽어온 블록 수입니다.
* 특징: 메모리에서 읽는 것(`cr`)보다 디스크에서 읽는 것(`pr`)이 수만 배 이상 느립니다. 최초로 쿼리를 실행할 때(Cold Buffer 상태) 많이 발생하며, 한 번 읽어온 블록은 메모리에 캐싱되므로 두 번째 실행할 때는 `pr`이 줄어들고 `m` 기반의 `cr`만 늘어나는 경향이 있습니다.
* 해석: `pr` 값이 지속적으로 높다면 인덱스가 없어서 테이블 전체를 풀 스캔(Full Table Scan)하고 있거나, 버퍼 캐시 메모리 자체가 부족하다는 신호입니다.

### `pw` (Physical Write) - 디스크 쓰기 (물리적 I/O)

* 의미: 메모리의 내용을 디스크(Temporary Tablespace 등)에 직접 기록한 블록 수입니다.
* 특징: 일반적인 `SELECT` 쿼리는 데이터를 읽기만 하므로 보통 `pw`가 0이어야 정상입니다. 하지만 대량의 데이터를 정렬(`ORDER BY`, `GROUP BY`)하거나 대용량 해시 조인(Hash Join)을 수행할 때, 메모리 공간(PGA의 Sort Area나 Hash Area)이 부족하면 오라클은 디스크의 임시 테이블스페이스(Temp Tablespace)에 중간 결과물을 썼다가 지우는 작업을 합니다.
* 해석: `pw`가 찍혔다면 메모리 부족으로 인한 디스크 스왑(Disk Swap)이 발생했다는 뜻이며, 성능이 급격히 떨어지는 주범입니다. (PGA 크기를 늘리거나 쿼리를 튜닝해야 합니다.)

## 2. 튜닝 관점에서의 종합 해석법 (Cheat Sheet)

실행 계획 결과 뷰에서 세 지표가 어떻게 조합되느냐에 따라 문제점을 바로 파악할 수 있습니다.

| 현상 | 원인 분석 | 해결 방향 |
| --- | --- | --- |
| `cr`이 과도하게 높음 | • 필요 이상으로 많은 블록을 읽음<br>

<br>• NL 조인 시 선행 테이블 필터링 실패로 무한 루프 | • 적절한 인덱스 생성 및 SQL 조건 최적화<br>

<br>• 대량 데이터인 경우 Hash Join 전환 유도 |
| `pr`이 계속해서 높음 | • Buffer Cache에 데이터가 없어 계속 디스크 조회<br>

<br>• Full Table Scan 빈발 | • 자주 쓰는 테이블/인덱스는 메모리에 상주<br>

<br>• 인덱스 스캔(Index Range Scan) 유도 |
| `pw`가 0보다 큼 (`pw > 0`) | • 정렬(Sort)이나 해시(Hash) 연산 중 PGA 메모리 부족으로 Temp DB 가동 | • `WORKAREA_SIZE_POLICY` 및 `PGA_AGGREGATE_TARGET` 점검<br>

<br>• 불필요한 대량 정렬 구문 제거 |

> 💡 공부하시면서 마주친 힌트 하나 더!
> 쿼리를 수행할 때 `cr` 수치가 올라가는 과정에서, 혹시 이전에 배운 UNDO 세그먼트의 상태가 매칭되시나요?
> `cr`을 생성하기 위해 UNDO를 찾아갈 때, 아직 `COMMIT`되지 않은 ACTIVE 상태나, `COMMIT`은 되었지만 유지 기간 내에 있는 UNEXPIRED 상태의 에컨트(Extent)들이 열일하며 과거의 데이터를 복원해 주는 덕분에 우리는 에러 없이 정확한 데이터를 볼 수 있는 것이랍니다.

현재 튜닝 중이신 실행 계획 란에 `pw`가 발견되어 정렬/해시 영역(PGA)을 확인 중이시거나, `cr`이 폭발하여 인덱스 스캔 효율을 고민 중이신가요? 구체적인 수치나 실행 계획 양식을 보여주시면 어떤 부분에 병목이 걸린 건지 더 자세히 짚어드리겠습니다!
