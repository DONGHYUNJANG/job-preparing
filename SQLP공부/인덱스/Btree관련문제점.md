## 정리
Index Skew
-> 리프노드 한쪽으로 치우침
Index Sparse
-> 리프노드값이 듬성듬성
문제점: 인덱스 효율이 떨어짐, Hot block 가능성 높아짐
해결책: Alter Index, Shirink
---

## 1. Index Skew (인덱스 불균형)

* 정의: 인덱스의 리프 노드(Leaf Node)가 한쪽 방향으로만 치우치는 현상입니다.
* 발생 원인: 주로 시퀀스(Sequence)나 날짜(Date)처럼 데이터가 항상 한쪽 끝으로만 지속적으로 증가(Ascending)하며 입력될 때 발생합니다. 대량의 과거 데이터를 지우고(`DELETE`) 새로운 데이터를 넣어도 기존에 비어버린 왼쪽 리프 노드는 재사용되지 않고 오른쪽으로만 인덱스 블록이 계속 늘어납니다.
* 특징: 오라클의 B-Tree 인덱스는 깊이(Depth)가 자동으로 균형을 맞추는 구조(Balanced Tree)이기 때문에 완전히 한쪽만 깊어지지는 않지만, 데이터가 없는 빈 블록들이 한쪽에 방치되어 공간 낭비를 초래합니다.

---

## 2. Index Sparse (인덱스 희소화)

* 정의: 인덱스의 리프 노드 블록들이 꽉 채워지지 못하고 듬성듬성하게 텅 빈 공간을 가지고 있는 현상입니다.
* 발생 원인: 테이블의 데이터를 무작위로 대량 삭제(`DELETE`)한 경우에 발생합니다. 오라클은 인덱스 엔트리가 삭제되어도 해당 블록의 공간을 즉시 OS에 반환하지 않고 비워둡니다. 새로운 데이터가 그 자리에 딱 맞게 들어오지 않으면 블록의 밀도가 낮아진 채로 유지됩니다.
* 특징: 지워진 자리에 새로운 데이터가 들어오면 재사용될 수 있지만, 대량 삭제 후 입력이 없거나 무작위 입력이 지속되면 밀도가 극도로 낮아진 채 방치됩니다.

---

## 3. 문제점

정리하신 대로 인덱스의 효율성이 극도로 떨어지고 병목 현상이 발생하게 됩니다.

* I/O 비용(스캔 효율) 저하: 원래는 1개의 블록만 읽으면 될 데이터를, 듬성듬성 비어있는 탓에 3~4개의 블록을 읽어야 하므로 `INDEX RANGE SCAN` 성능이 크게 떨어집니다.
* 메모리(Buffer Cache) 낭비: 데이터가 없는 빈 껍데기 블록들까지 데이터베이스 버퍼 캐시에 올라오므로 메모리 공간을 비효율적으로 점유합니다.
* Hot Block(경합) 가능성 증가: 특히 Index Skew 상태에서 새로운 데이터가 계속 오른쪽 끝 블록으로만 밀려 들어오면, 여러 세션이 동시에 최우측 블록을 수정하려고 하면서 `buffer busy waits`나 `latch: cache buffers chains` 같은 대기 이벤트가 발생하여 시스템이 느려집니다.

## 4. 해결책 (인덱스 재구성)

### ① `ALTER INDEX ... REBUILD`

* 인덱스를 아예 처음부터 새로 가공하여 재생성하는 방식입니다.
* 특징: 듬성듬성한 공간이나 치우친 노드들이 완전히 칼같이 정렬되므로 성능 개선 효과가 가장 확실합니다.
* 주의점: 인덱스를 새로 만드는 동안 임시 세그먼트 공간이 필요하며, `ONLINE` 옵션을 주지 않으면 테이블에 락(Lock)이 걸려 DML이 차단될 수 있습니다.

### ② `ALTER INDEX ... COALESCE` (결합)

* 동일한 가지(Branch) 내에 있는 이웃한 리프 블록들을 합쳐서 공간을 조밀하게 만듭니다.
* 특징: `REBUILD`와 달리 새로운 공간을 요구하지 않고, 락(Lock)을 최소화하여 서비스 중에도 가볍게 수행할 수 있습니다. 다만, 완전히 새로 만드는 것이 아니라 옆 블록과 합치는 수준이라 Skew/Sparse가 완벽히 해결되지 않을 수 있습니다.

### ③ `ALTER TABLE ... SHRINK SPACE` (쉬링크)

* ASSM(Automatic Segment Space Management) 환경에서 테이블이나 인덱스의 빈 공간을 쥐어짜서(HWM, High Water Mark를 아래로 내려서) 남는 공간을 데이터파일에 완전히 반환하는 방식입니다.
* 특징: 인덱스 세그먼트에 직접 수행하여 `REBUILD` 없이도 단편화를 제거하고 디스크 공간을 확보할 수 있습니다.
