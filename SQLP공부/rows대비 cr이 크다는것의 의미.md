오라클 실행 계획이나 트레이스 결과에서 반환된 로우 수(`Rows`)에 비해 `cr`(Consistent Read, 논리적 메모리 읽기) 수치가 압도적으로 크다는 것은, 튜닝 관점에서 "데이터를 몇 건 안 건지기 위해 메모리(블록)를 엄청나게 헤집고 다녔다"는 뜻입니다.

즉, I/O 효율성이 극도로 떨어진 비효율적인 상태를 의미하며, CPU 사용량을 폭증시키고 시스템 전체를 느리게 만드는 주범입니다.

이 현상이 발생하는 대표적인 원인 4가지를 명확하게 짚어드리겠습니다.

---

## 1. 인덱스 스캔 후 '테이블 랜덤 액세스' 폭발 (가장 흔한 원인)

인덱스를 타긴 탔는데, 인덱스 조건으로 데이터가 걸러지지 않고 테이블로 넘어가서 필터링될 때 발생합니다.

* 상황: 인덱스로 100,000건을 찾아서 테이블 블록 100,000개를 읽으러(`cr` 폭발) 갔는데, `WHERE` 절의 나머지 조건에 의해 최종적으로 5건(`Rows`)만 살아남은 경우입니다.
* 이유: 인덱스 컬럼 구성이 잘못되었거나, 선행 필터 역할을 해야 할 조건이 인덱스에 포함되지 않아 테이블을 일일이 방문하며 필터링(Post-Filtering)했기 때문입니다.
* 해결책: `WHERE` 절의 다른 필터 조건 컬럼을 인덱스 뒤에 결합하는 결합 인덱스(Composite Index)를 생성하여, 테이블로 가기 전에 인덱스 단계에서 먼저 필터링되도록 해야 합니다.
-> 결국 인덱스에서 가져올 블럭을 좁히지 못했기 때문에 발생한것임
---

## 2. Nested Loops Join의 선행 테이블 필터링 실패 (무한 루프)

앞서 질문하셨던 "NL 조인의 선 필터링 경향"과 직결되는 문제입니다.

* 상황: Outer(Driving) 테이블에서 필터링이 안 돼서 50,000건이 살아남았습니다. 이 50,000건이 Inner(Driven) 테이블의 인덱스를 50,000번 반복해서 탐색(`cr` 폭발)합니다. 그런데 최종 조인 결과 매칭된 데이터는 고작 10건(`Rows`)뿐인 경우입니다.
* 이유: NL 조인은 선행 테이블에서 데이터를 확실히 줄여놓고 진입해야 하는데, 그러지 못해 조인 루프 횟수가 과도하게 늘어났기 때문입니다.
* 해결책:
* 선행 테이블의 필터 조건을 만족하는 인덱스를 정비하여 드라이빙 건수 자체를 줄입니다.
* 데이터량이 많다면 NL 조인 대신 대량 처리에 유리한 Hash Join으로 유도(`/*+ USE_HASH */`)합니다.



---

## 3. 인덱스 컬럼의 '낮은 선택도 (Low Selectivity)'

인덱스 자체의 변별력이 없어서 발생하는 문제입니다.

* 상황: 성별(`남/여`), 상태값(`정상/해지`)처럼 데이터 종류가 몇 개 안 되는 컬럼(Low Cardinality)에 인덱스가 걸려있을 때입니다.
* 이유: 인덱스를 읽을 때마다 수천, 수만 건의 매칭 블록을 다 긁어오느라 `cr`은 치솟는데, 정작 최종 결과물(`Rows`)은 몇 건 안 되는 비효율이 발생합니다.
* 해결책: 이런 컬럼은 단독 인덱스로 쓰면 안 되며, 다른 변별력 높은 컬럼과 묶어서 결합 인덱스로 구성하거나 Full Table Scan이 오히려 나을 수 있습니다.

---

## 4. Full Table Scan 후 대량 필터링

테이블의 처음부터 끝까지 모든 블록을 다 읽었는데, `WHERE` 조건에 맞는 데이터가 거의 없을 때입니다.

* 상황: 테이블 전체 크기가 10GB(약 120만 블록)라 한 번 읽을 때마다 `cr`이 1,200,000씩 찍히는데, 최종 결과 화면에 나오는 건 단 1건(`Rows = 1`)인 경우입니다.
* 이유: 적절한 인덱스가 없어서 오라클이 어쩔 수 없이 무식하게 전체를 다 읽어 내려갔기 때문입니다.
* 해결책: 조회 조건에 맞는 적절한 인덱스를 생성해 주는 것이 가장 확실한 처방입니다.

---

## 🔍 요약 및 기준점

일반적으로 튜닝 전문가들은 `cr / Rows` (Row당 읽은 블록 수) 비율을 봅니다.

* `cr / Rows <= 5 ~ 10`: 아주 이상적이고 효율적인 쿼리입니다.
* `cr / Rows >= 100 이상`: 1건을 얻기 위해 100개 이상의 블록을 읽는 상태이므로, 무조건 튜닝 대상으로 선정하고 위의 4가지 원인 중 어디에 해당하는지 실행 계획을 뜯어봐야 합니다.

지금 분석 중이신 쿼리 트레이스에서 `Rows` 대비 `cr` 수치가 대략 어느 정도 비율로 깨져있나요? 실행 계획 상의 스캔 방식(Index Range Scan, Full Table Scan 등)과 함께 말씀해 주시면 어디서 비효율이 새고 있는지 바로 진단해 드릴 수 있습니다!
